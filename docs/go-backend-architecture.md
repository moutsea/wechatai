# Go 后端与 Cloudflare 站点拆分

## 范围与交付状态

React 前端、登录、OAuth、Stripe 支付入口和 D1 用户与订单留在 Cloudflare，媒体继续存放在 R2。VPS 按功能承接消耗 DO 资源的工作，新增后端能力使用原生 Go。长期目标是替换 `PersonalAccount` 和 `ReminderScheduler`，每次发布可以只迁一项功能。

微信接收、空闲连接巡检和耗时任务执行各有独立开关。先选功能，再用账户名单控制这项功能的覆盖范围。例如，仅交接巡检时，VPS 检查会话心跳，消息、任务状态和扣费仍由原账户 DO 写入。以后交接持久数据时，需要一并迁移依赖同一事务的写入。只有通过 `account_backend_routes` 让 Go 接管整个账户时，才要求完整账户能力就绪。

Go 服务使用 VPS 本地 SQLite 保存账户数据。现有 receiver、executor 的协议在过渡期间继续支持。公开仓库的检查使用 GitHub 托管 runner；发布使用同一套可本地运行的脚本。

本文先确定大模块及其交互，再约定内部组件和原子操作。设计不等于实现；生产切换必须以实际通过的功能与迁移验收为准。

## 大模块及职责

| 大模块 | 拥有的数据与职责 | 对外提供 | 不负责 |
| --- | --- | --- | --- |
| Cloudflare edge | 登录会话、OAuth、Stripe 验签、D1 订单、管理员身份、账户路由 | 经过身份和权限核验的账户命令；有界的 D1/R2 操作 | VPS 钱包表、账户 SQLite、模型执行 |
| accounts | 原账户 ID、账户数据库生命周期、迁移阶段、路由版本 | 打开指定账户、事务入口、迁移写入隔离 | 支付供应商、插件规则、任意用户指定的文件路径 |
| credits | credits 桶、不可变账本、旧预扣、欠额、平台计量 | 发放、每日补足、扣费、释放旧预扣、查询余额 | Stripe HTTP、消息发送、模型调用 |
| conversation | 模型与插件配置、会话、消息、上下文及任务生命周期 | 配置命令、开始/恢复会话任务、完成结果 | 自行判定登录身份、直接发送微信、改写其他模块的账本 |
| delivery | 微信绑定、收件箱、发件箱、远程连接器和媒体交付 | 入站去重、任务领取、结果接收、可恢复投递 | 直接决定业务扣费、改变订单状态 |
| automation | 提醒、通知、会员提醒、到期清理与重试 | 持久化排期、到期任务执行与重新排期 | 只靠内存保存待办、执行自由格式 SQL |
| jobs | 作业状态、领取租约、重试时间、结果及幂等指纹 | 原子入队/领取/确认/延迟、崩溃后的过期任务处理 | 自动重跑结果未知的外部副作用 |
| integrations | LLM、云端 Agent、R2 和受控处理器的协议适配 | 有超时、限长和取消语义的外部调用 | 保存钱包或账户权威状态 |
| migration | 全量导出/导入、校验清单、原 ID 与路由版本、恢复记录 | 冻结、校验、导入和切换准备 | 静默覆盖已经产生新写入的目标数据库 |
| app/httpapi | 组装、内部 HTTP 协议、请求鉴权、健康状态、进程关闭 | 将可信命令交给对应应用服务 | 在路由处理器中实现钱包或 SQL 业务规则 |

`platform` 仅提供配置、SQLite 驱动、加密、时钟等基础能力。它不导入业务模块。业务模块不导入 `app` 或 `httpapi`；跨模块操作由应用服务显式编排，禁止跨模块修改私有表。

## Go 接管整个账户后的模块交互

1. 浏览器及连接器仍访问原站点地址。Worker 验证用户或有限权限凭据，从 D1 读取可信账户 ID、后端位置和路由版本。
2. Worker 对内部请求的版本、方法、路径、时间、请求 ID 和正文摘要签名。Go 校验独立的后端凭据与路由版本，不信任浏览器提交的账户身份。
3. 普通配置命令由账户内的短事务完成。耗时任务先持久化意图，再离开事务执行外部 I/O；返回后重新验证账户、链接、会话版本和作业租约。
4. 结果、消息历史、计量、扣费和发件箱在同一账户数据库中提交。微信发送完成后再确认发件箱；重复确认不重复扣费。
5. Stripe 仍在 Worker 验签并持久化订单，通过固定支付事件 ID 调用 Go 的授权发放命令。网络确认丢失时重放同一事件，不创造新操作 ID。
6. 邀请奖励由 Worker 从 D1 查验资格和收款角色，Go 在目标账户事务内按原奖励 ID 入账。两笔奖励分别提交。当前由原 DO 持久化重试，双方成功后再将 D1 状态更新为 `rewarded`。
7. 调度器从数据库恢复到期工作。内存中的定时器和唤醒通知只作加速；进程重启后可以重新构建。发现用的汇总索引不是作业权威状态。

保留 Worker 中的 D1/R2 绑定不等于把任意 SQL 或存储管理接口暴露给 VPS。跨边界操作必须有明确用途、权限和大小限制。

## 已可单独交接的接收器巡检

微信接收器在 VPS 保管接收游标，使用带心跳的休眠 WebSocket 递交真实消息。独立的 Go 巡检进程在同一台 VPS 上核对健康会话。Worker 的 D1 登记仅保存会话、账户和重试时间。正常巡检读取登记并更新全局心跳。遇到缺失会话时，Worker 原子认领该次恢复，再由账户核对当前连接。迟到的旧会话、重复回报和中途失败均可安全重试。生产业务账本、消息和原账户 ID 的所有权在这次交接中仍属于原 DO。

## 小模块与原子边界

### 账户存储

- `platform/sqlite`：连接参数、短事务、带校验和的数据库迁移。事务回调只执行本地数据库操作；异常或 panic 均回滚。
- `accounts`：验证 64 位十六进制账户 ID、账户文件权限、连接生命周期和迁移版本。保留旧 ID，不使用用户名构造文件路径。
- 同一账户的状态变更由 SQLite 事务及有条件更新保护。模型请求不持有数据库事务；取消、结果回传和其他账户不能被网络等待阻塞。

### 钱包与计量

- 发放：检查同一发放 ID、创建 credits 桶、抵扣欠额、追加账本为一次事务。
- 每日额度：使用北京时间日期与历史已发放总额，仅补足差额；使用额度后重放不能重新发满。
- 扣费：固定结算 ID 去重、按到期顺序扣桶、记录欠额和不可变账本为一次事务。
- 旧预扣：分配与账本同时提交；结算或释放只能成功一次，保留原到期语义。
- `cl100k_base@gpt-tokenizer-4.0.0` 及计费规则保持兼容。替代实现必须先做中文、Unicode、特殊文本及截断的一致性验证。

### 作业与投递

- 入队：同一 ID 与同一指纹重放返回原作业；同一 ID 不同内容返回冲突。
- 领取：在一次事务中选取到期作业、更新领取状态、生成新租约并增加尝试次数。
- 完成：校验当前租约、状态与到期时间后保存结果；旧租约不能确认新任务。过期的原执行租约可以保存核对回执，正常消费者只取按时完成的结果。
- 执行器在专用签名地址领取和回报。普通 JSON 命令上限为 2 MiB，执行器正文上限为 32 MiB。签名覆盖账户、路由版本、操作及正文摘要。Go 先验证签名，收到完整正文并核对摘要后才更新任务。带摘要的请求可直接流式转发；旧客户端由边缘在限额内暂存并计算摘要。
- 已完成的输入及时释放。取走结果和下游业务写入共用事务，提交后仅保留幂等指纹。结果未知的任务保留核对所需的信息。
- 延迟：校验租约，持久化下一次尝试时间后释放领取状态。
- 外部结果未知：进入需要核对或明确失败的状态，不自动重新执行可能计费或产生副作用的调用。
- 发送微信时复用原发送 ID 和正文。上游已接收但响应丢失时，最终去重仍受微信接口能力限制。

### 调度

- 个人提醒、消息通知、会员提醒分别拥有排期版本和处理状态。
- 编辑、取消、会员变化和链接重绑优先于旧的领取结果；所有外部 I/O 之后再检查版本。
- 一个调度任务失败不阻塞其他账户。worker 数和等待队列有上限，关闭进程时停止领取并保留未完成记录。

## 数据迁移与切换

1. 覆盖全部 D1 用户及已有 DO，包括未活跃账号；建立 `userId → 原 accountId` 清单。
2. 对账户停止新工作并排空已接受请求。Go 账户存在有效作业租约时持久化 `draining`，继续接收原租约回报，调用方重试冻结。租约排空后持久化 `frozen`，禁止旧 alarm、RPC、回调和连接器继续写入。
3. 导出完整表结构、行、BLOB、SQLite 序号、需要保留的调度元数据及校验清单。加密凭据保留原密文、密钥和 additional data 上下文。
4. 导入暂存目录，核对逐表数量、摘要、账户 ID、钱包与账本、预扣、消息游标、支付去重、待交付结果和排期。
5. 校验通过后激活目标并切换路由版本。旧端和旧租约不能覆盖目标的新状态；同一账户始终只有一个写入方。
6. 保留旧数据只读供核对。目标产生新数据后的回滚必须包含这些新数据，不能把流量直接切回旧快照。
7. 完成验收与备份恢复演练后，才移除 DO 绑定并清理旧数据。旧数据保留期间仍计入 DO 存储用量。

## 部署与检查

- `frontend` 与 `backend` 独立构建，公开仓库使用 GitHub 托管 runner；不再依赖私有 SG 排队与轮询控制器。
- Pull Request 只运行无生产凭据的检查。生产发布仅使用受信分支和独立环境凭据。
- 后端以固定提交构建版本化产物，先安装到新 release 目录，检查配置、数据库兼容性及健康状态，再切换运行版本。
- 发布代码与迁移账户数据是两种独立操作；常规部署不隐式迁移、覆盖数据库或重新生成加密密钥。
- 前端在对应后端协议通过验证后发布。回退二进制之前检查数据库 schema 的向后兼容性。

## 验收口径

区分 Go 单元测试、真实 SQLite 集成测试、外部接口模拟、真实供应商联调和生产验收。未实现功能、被筛选掉的测试和设计说明均不计为链路通过。

必须验证：真实消息接收至回复和扣费、重复入站消息、重复支付回调、撤销凭据、重绑/删除链接、个人记录及提醒、云端 Agent 回调与文件、服务重启、旧租约结果、账户切换、备份恢复和包含新写入的回退。
