# Go 后端与 Cloudflare 入口的独立发布

## 当前实现状态

发布时先选择要交接的功能，再决定覆盖哪些账户。前端、登录和支付入口继续由 Cloudflare 提供。生产已将微信接收和空闲连接巡检交给 VPS，账户业务数据继续由原 DO 写入。

| 发布范围         | 切流方式                                                     | 验收重点                                                                               |
| ---------------- | ------------------------------------------------------------ | -------------------------------------------------------------------------------------- |
| 微信接收         | `WECHAT_RECEIVER_ACCOUNTS`                                   | VPS 先持久化收到的消息，Worker 确认后清除待交付批次。断线重连能补交待确认消息。        |
| 空闲连接巡检     | `WECHAT_RECEIVER_WATCHDOG_ACCOUNTS`，作用于 VPS 已接收的账户 | 健康连接交给 VPS 巡检，失联时 Worker 能恢复接收。                                      |
| 微信聊天耗时任务 | `EXECUTOR_ACCOUNTS`                                          | VPS 执行受支持的模型和工具调用，原 DO 认领结果并结算。核对重传时的上游调用次数和扣费。 |
| 整账户数据与业务 | `account_backend_routes`                                     | 完整账户能力、冻结、导入和切换均通过验收，确认只有一处写入账户数据。                   |

前三项可以分别灰度和回退。账户名单中的 `all` 只扩展对应功能的覆盖范围。下文的账户 SQLite 和签名命令描述整账户方案的开发进度。

已实现：账户 SQLite 生命周期及事务、兼容 Worker 的凭据加密、钱包与支付结算、会员赠送及排期状态、持久作业队列、调度执行引擎、签名命令协议、Go HTTP 服务、VPS 在线备份、独立构建和发布控制流程。

Go 已接入账户身份、钱包和支付结算、会员赠送、后台统计、邀请奖励、连接器升级通知。账户 API 已接入引导状态、会话及消息历史、角色摘要读取、个人助理记录的分库查询和账目汇总、云任务详情和分页、云空间用量、任务取消、通知凭据与回执，以及 OpenClaw、Hermes、Muse 的配对码签发、令牌轮换、撤销与状态读取。通知投递和会员到期提醒使用 VPS 上的原生调度器，接收队列和重试时间保存在账户 SQLite。连接器安装命令与升级说明由提供下载文件的 Worker 生成。

浏览器账户 API、通知令牌、云任务回调、支付到账、邀请奖励和管理员账户操作按 D1 的 `account_backend_routes` 查找账户。没有路由记录的账户继续由原 DO 处理。Go 账户的附件下载经过两次授权检查，之间由 Worker 读取原 R2 对象。部署此开发版本的入口前须应用 `0019_account_backend_routes.sql`。边缘使用 `WECHATAI_BACKEND_ORIGIN` 和 `WECHATAI_RPC_SECRET`，Go 使用对应的签名密钥和与边缘一致的 `APP_URL`。冻结、身份不匹配和后端不可用时，已分配的账户请求会失败，防止写回另一份账户数据。

已接入原生 Go 微信接收。外置接收器可通过已验签的 WebSocket 提交批次；没有外置连接时，VPS 自行长轮询 iLink。两条路径共用账户事务，确认收件后才推进游标。

AGT 回调先由 Worker 验证路由令牌并限制请求体，再由 Go 使用任务创建时的密钥版本验证原始正文和工作区归属。回执哈希和任务唤醒时间在同一个 SQLite 事务提交。重复投递保留已保存的退避时间，终态任务保持原结算结果。使用独立密钥环时，VPS 须配置与 Worker 一致的 `AGT_CALLBACK_KEYS` 和 `AGT_CALLBACK_KEY_VERSION`。查询已有云空间还需 `AGT_ORIGIN`、`AGT_APP_ID`、`AGT_TENANT_ID` 和 `AGT_APP_KEY`。

整账户切流仍需完成聊天与模型执行、插件业务、个人记录写入和提醒、微信绑定管理与回复、连接器任务中继、云端任务执行与结算，以及独立定时器和外部执行器的路由。线上 DO 冻结导出、批量导入和切换尚待演练。生产环境当前使用的微信接收巡检与以上账户业务独立。

`/readyz` 和 `wechatai check-ready` 检查整账户服务的 RPC、API 操作、流式接口和后台运行能力。当前仍有缺项，因此整账户切流须等待。按功能部署的接收器、巡检和耗时任务执行器分别使用自己的验收流程。

### Grok Bot 的 Routine 派发

Grok Bot 使用个人微信账户原有的任务队列、计量和回复投递。新任务由 VPS 上的 Go 服务向 Routine 发一次 Webhook，Grok 通过 Worker 的 `/api/grok/mcp` 领取任务并回传文字。空闲时没有连接器轮询。Go 将派发回执写入账户目录上一级的 `grok-wakes.sqlite`，仅记录任务 ID、状态和时间。后续派发会清理超过 24 小时的回执。发布时先更新 Go，再更新 Worker。明确未发送或 Routine 限流时最多尝试三次。响应丢失时等待原任务领取，到 45 分钟期限仍未完成则按失败结算。账户已冻结或已迁至 Go 时，Grok MCP 请求会被拒绝。

1. 在 Go 服务环境配置独立的 `GROK_DISPATCH_SECRET` 或 `GROK_DISPATCH_SECRET_FILE`（至少 32 字节的随机密钥），发布 Go 程序并重启。待命模式也能独立提供这个签名校验接口。
2. 在既有 TLS 反向代理上将 `POST /internal/v1/grok/wake` 转给 Go 监听地址。在 `edge-production` 的私有 `WRANGLER_CONFIG` 中将 `env.production.vars.GROK_DISPATCH_ORIGIN` 设为该 HTTPS 源，并配置同值的 Worker Secret `GROK_DISPATCH_SECRET`。两项齐备后插件页才开放配置。
3. 在自己的 Grok Bot 桌面端创建 Webhook Routine，把 POST 地址和 key 填入微伴。支持 `https://api2.cursor.sh/automations/webhook/<id>`。微伴生成的 MCP 凭据仅供该插件配置使用，按页面说明通过自定义 Remote HTTPS 连接器传入。团队管理员需允许这个 MCP 服务。[Routine 官方说明](https://docs.x.ai/grok-bot/skills-routines-and-automations) · [自定义连接器官方说明](https://docs.x.ai/grok-bot/computer-and-apps)
4. 从微信发一条任务和一条追问，核对回复进入原微信、上下文和扣费。Webhook 成功仅表示已受理。每个任务最多唤醒三次；工具只允许一次成功领取。45 分钟内未完成的任务按失败处理，不扣平台 credits。发布或模拟测试均不能替代真实 Bot 验收。

### 可独立灰度的 VPS 任务

运行 `pnpm build:receiver` 独立打包接收器和 `receiver-watchdog`。巡检进程读取本机接收器会话，通过 Worker 核对 D1 登记并报告失联。发布时沿用当前账户数据和路由。接收器发布说明列出了灰度开关、版本兼容和回退延迟。[接收器发布说明](../integrations/wechat-receiver/README.md#按账户把空闲连接巡检迁到-vps)

## 构建与本地验证

```sh
pnpm check:backend
pnpm test:backend-executor
node --test scripts/backend-artifact.node-test.mjs
python3 -m unittest discover -s backend/deploy -p 'test_*.py'
pnpm build:backend
pnpm build:edge
```

Go 使用 `backend/go.mod` 的固定工具链，构建纯 Go Linux 二进制，默认 `amd64`，可用 `WECHATAI_BUILD_ARCH=arm64` 构建另一种架构。产物在 `backend/dist/linux-ARCH/`，包含二进制和带提交、协议、架构、SHA-256 的 manifest。

工作区有未提交改动时，版本带 `-dirty`；可以本地构建和查看部署计划，真实发布会拒绝。可审查代码提交后再构建发布。

账户服务模式需要独立 RPC 密钥和原 `ENCRYPTION_KEY`。可以通过 `WECHATAI_RPC_SECRET_FILE`、`ENCRYPTION_KEY_FILE` 指向私有文件，Go 与原 Worker 使用相同的规则去除账户加密密钥首尾空白。RPC 签名密钥按文件原始字节读取，两端必须一致。`WECHATAI_DATA_DIR` 必须是权限为 `0700` 的私有目录，默认监听 `127.0.0.1:8088`。

## VPS 首次准备

首次部署需要 Linux、systemd、Python 3、独立 `wechatai` 服务用户，以及具有受限部署权限的 SSH 用户。应用二进制不以 root 运行。

1. 创建 `/opt/wechatai/releases`，由 root 拥有，目录可供服务用户读取。
2. 创建 `/var/lib/wechatai/accounts`，由 `wechatai:wechatai` 拥有，权限 `0700`。
3. 将 `backend/deploy/backend.env.example` 复制到 `/etc/wechatai/backend.env`，文件由 root 拥有且权限 `0600`。首次待命部署只需设置 `WECHATAI_DEPLOY_MODE=standby`。交接账户时切换为 `accounts` 并设置原 `ENCRYPTION_KEY` 和独立 RPC 密钥。
4. 将 `backend/deploy/wechatai-backend.service` 安装为 `/etc/systemd/system/wechatai-backend.service`，将 `backend/deploy/release.py` 安装为 root 拥有、权限 `0755` 的 `/usr/local/libexec/wechatai-release`。部署用户不能修改这些文件。
5. 为部署用户配置仅运行该发布程序的免交互 sudo 权限；不要开放任意 shell 或 systemctl。部署权限等同于发布受信任的后端代码，不授予外部 PR。
6. 运行 `systemctl daemon-reload`。发布后启用 `wechatai-backend.service`，已有接收器、巡检和执行器继续独立运行。

默认仅监听回环地址。远程 Worker 接入需要独立的 HTTPS 入口、证书和明确的路径转发；内部接口仍校验签名。该 HTTPS 入口尚未配置或实测，不要把明文 8088 暴露到公网。

自定义数据目录和监听端口时，在 `/etc/wechatai/backend.env` 设置 `WECHATAI_DATA_DIR` 和 `WECHATAI_LISTEN`。发布程序通过 systemd 临时服务运行候选二进制的 `deployment-settings`，只读取生效的数据路径和探活地址。端口须固定，监听通配地址时使用对应的回环地址探活。数据放在 `/var/lib/wechatai` 下可直接使用现有服务权限。若使用外部挂载目录，需给服务用户读写权限，并在 systemd 服务的 `ReadWritePaths` 加入该路径。更新已有安装时须同步更新 root 管理的发布程序和服务单元，再执行 `systemctl daemon-reload`。

## 本地发布

设置以下环境变量，SSH 密钥通过文件提供：

| 变量 | 内容 |
| --- | --- |
| `WECHATAI_VPS_HOST` | 已核验的 VPS 主机名或 IPv4 地址 |
| `WECHATAI_VPS_USER` | 独立部署用户 |
| `WECHATAI_SSH_KEY_FILE` | 权限 `0600` 的 SSH 私钥文件 |
| `WECHATAI_SSH_KNOWN_HOSTS_FILE` | 已通过可信渠道核验的主机公钥文件 |

```sh
pnpm build:backend
pnpm deploy:backend --dry-run
pnpm deploy:backend
```

脚本启用严格主机密钥校验。它不会临时信任 `ssh-keyscan` 返回的未知主机，也不会把私钥或应用密钥放到命令行。

发布步骤为：核对产物 → 私有临时目录上传 → 发布互斥锁 → 核对版本、功能和数据兼容性 → 停旧进程 → 再次检查数据 → 原子替换 `current` → 启动并按配置模式核对探针和提交版本。不会自动切换账户路由、删除旧 release、迁移 D1、清理 DO 或替换密钥。

待命进程监听回环地址。`/healthz` 返回提交版本和 `mode=standby`，`/readyz` 返回 503，账户业务路径返回 404。设置 `GROK_DISPATCH_SECRET` 后，待命进程还提供签名验证的 Grok Routine 转发。发布前和启动时校验账户目录为空，账户存储、业务路由和调度器在账户模式初始化。账户模式须同时通过 `/healthz` 和 `/readyz`。发布器用当前模式的验收结果记录 `last-healthy`。接管旧安装时，先探测 `current` 所指的提交。候选启动失败时，先停服务并撤下 `current`，再由上次健康版本检查数据兼容性。兼容时恢复链接，清除 systemd 启动限流，重启并复验该模式的探针。首次启动失败、旧版本无法读取数据或回滚探针失败时，服务停用，发布目录保留供诊断。代码回退和迁移后数据回退是不同操作，不能用旧快照覆盖新写入。

## GitHub Actions

`CI` 在 GitHub 托管 runner 运行站点、Go 和秘密扫描，不再依赖 SG 控制仓。

推送到 `main` 后，`CI` 的 `check`、`secrets` 和 `backend` 三个任务全部成功，才会并行调用以下两个发布工作流。每个工作流发布前会核对提交是否仍是远端 `main` 的最新版本。每一端串行发布，进行中的生产操作会执行到结束。需要单独重试时，可在 Actions 中选择对应工作流，选 `main` 并点 **Run workflow**。

| Workflow / Environment | Variables | Secrets |
| --- | --- | --- |
| `Deploy Go backend` / `backend-production` | `VPS_HOST`、`VPS_USER` | `VPS_SSH_PRIVATE_KEY`、`VPS_KNOWN_HOSTS` |
| `Deploy Cloudflare edge` / `edge-production` | `CLOUDFLARE_ACCOUNT_ID` | `WRANGLER_CONFIG`（完整私有 JSONC 配置）、`CLOUDFLARE_API_TOKEN` |

环境限制为受信任的 main，按项目需要设置环境审核人。PR 检查没有生产凭据；不使用 `pull_request_target` 执行外部代码。Cloudflare 已有应用 Secrets 在常规发布中保留，不把它们写入 JSONC 或构建产物。

后端发布采用 VPS 环境文件指定的模式，账户模式始终要求完整能力就绪。待命部署时先确认生产 D1 只待应用 `0019_account_backend_routes.sql`，应用后检查路由表行数为零，再发布 Worker。Cloudflare 发布暂时仍保留 DO 和独立提醒 Worker，不能提前删绑定或运行删除类迁移。

## VPS 备份与二进制兼容性

使用服务用户执行：

```sh
/opt/wechatai/current/wechatai check-data /var/lib/wechatai/accounts
/opt/wechatai/current/wechatai backup-data /var/lib/wechatai/accounts /PRIVATE_BACKUP_PARENT/new-generation
```

`check-data` 先以服务用户身份核对运行目录权限为 `0700`、可读写且可进入，再在只读事务中核对 schema 版本、校验和、账户身份和钱包表。`inspect-data` 用于只读检查导出目录，也可识别兼容的旧版本。已绑定的 Go 库必须具备候选版本的完整迁移记录。原始和未绑定 DO 快照须包含当前受支持的 PersonalAccount v1 的 46 张业务表及其必需列，并通过 ownerId、钱包和会员记录检查。缺表、缺列或缺欠额行均会中止核验。缺少身份的旧导出应先依据 D1 用户与原 DO 的映射单独核对。

`backup-data` 使用 SQLite 在线备份 API，包含已提交的 WAL、BLOB、NULL、rowid 和 AUTOINCREMENT 序号，不复制正在写入的主文件冒充备份。目标目录必须不存在；只有写入完整 `manifest.json` 的一代备份才可使用，失败留下的部分文件需单独核对。每个账户内是一致快照，不宣称多个独立账户处于同一事务时点。

备份仍包含账户私有数据和加密凭据，使用私有存储并单独保管原加密密钥。当前已验证 SQLite 备份内容可重新打开并恢复序号；批量生产恢复、路由版本提升及备份异机恢复尚未实现或验收。

### 恢复已有 Go 迁移记录的未绑定账户

使用原 Cloudflare 环境中的 D1 用户 ID 和 `ACCOUNTS.idFromName(userId).toString()` 独立取得账户映射，保存为本地 JSON 文件。文件格式如下，示例字符串需替换为原环境的实际值。

```json
{"format":"wechatai-original-identity-v1","accountId":"原命名空间中的64位十六进制ID","userId":"原D1用户ID"}
```

```sh
wechatai recover-unbound "$backup_dir" "$new_dir" "$account_id" "$user_id" "$next_epoch" "$identity_file"
wechatai check-data "$new_dir"
```

命令对照映射、命令参数、备份清单和库内所有者，核对源阶段为 `unbound`、源 epoch 为 0，只在新目录生成 `prepared` 副本。映射的来源由操作人核实；离线程序自身无法证明一个手写文件来自原环境。若缺表、缺列或无法独立核对身份，应从运行过相应业务迁移的原 DO 重新导出。表结构检查无法发现上游已经删掉的单行业务数据。

## 本轮审查修复记录

| 链路 | 根因与改动 | 验证及边界 |
| --- | --- | --- |
| 功能注册 → 发布与激活 | RPC 注册表只认识方法名。应用现在汇总方法、API 操作、流接口和运行模块的注册结果，三个入口共用缺项算法。 | 本地检查了完整模块清单返回 200、抽去运行模块返回 503。该轮检查时缺 78 项。 |
| Cloudflare 发布 | pnpm 内置的 deploy 命令遮住了同名项目脚本。发布别名显式调用 pnpm run deploy。 | 用公开配置实际运行两层脚本，Wrangler 完成构建并以 dry-run 成功退出。 |
| GitHub Actions → VPS | SSH 文件路径写入环境文件后要到下一步才可见。准备凭据与运行部署脚本分为两个步骤。 | 用虚拟凭据、独立 shell 和真正的部署脚本完成 dry-run。 |
| 配置 → 内部鉴权 | 公开的示例值达到长度要求。示例改为留空，服务也拒绝旧占位符。 | Go 配置测试覆盖遗漏与旧示例。 |
| 订单 → 账户钱包 | 缺失或为 null 的字段曾被解为零。充值和订阅按类型校验后才写入支付去重记录。 | 本地签名 HTTP 与 SQLite 验证无效事件、同 ID 修正后入账和重放，保留订阅合法零值。 |
| 密钥配置 → 历史凭据 | 两端首尾空白处理不同。账户加密密钥按 Worker 规则处理，RPC 签名继续使用原字节。 | 环境变量与文件均用 Worker 密文验证过。 |
| 作业领取 → 执行器确认 | 旧租约不符合执行器 UUID 格式。领取生成 UUID v4。过期的原执行租约保留核对回执，无法匹配的租约返回 stale。 | 用仓库的 Node 执行器和本地 Go HTTP 服务验证领取、执行、回报以及待发文件删除。 |
| 附件 → 执行器 | 普通命令上限曾截断较大的附件。专用签名地址支持原始执行器正文，传输上限与旧 Worker 共用配置。 | 真实 Node 执行器、签名转发和本地 Go 服务完成了 31 MiB 输入与 31 MiB 结果的往返，业务附件处理器使用测试替身。Worker 测试覆盖带摘要的流式上传、旧客户端及超限拒绝。 |

| 本轮问题 | 根因与代码改动 | 验证与剩余边界 |
| --- | --- | --- |
| 冻结期间的执行回报 | 内存门只能等待单次 HTTP 调用。冻结事务现在恢复过期租约并检查有效租约，有任务在执行时持久化 `draining`，返回 `409 account_draining`。这时新写入和领取暂停，原执行器仍可提交回报。重试同一冻结请求会重新检查租约。 | 签名 HTTP 与 SQLite 验证排空跨进程实例重启、继续回报、最终冻结和已入库回执的重复确认。冻结后只允许确认已记录的相同结果。 |

先将原 DO 导出为独立、仅所有者可访问的 SQLite 文件（通常为 `0600`），并纳入已提交的 WAL。用 `backup-data` 生成一代完整备份，再执行 `wechatai prepare-legacy <backup-directory> <new-staging-directory> <account-id> <owner-id> <route-epoch>`。准备过程在独立目录核对文件名、字节数、SHA-256、账户身份及源阶段，并拒绝附带有效内容的 WAL 或回滚日志。成功后生成 `prepared` 账户。校验依据是受信任的备份清单，备份目录和清单应一同妥善保管。

已绑定的旧 Go 账户使用 `wechatai upgrade-account <backup-directory> <new-staging-directory> <account-id> <owner-id> <route-epoch>`。先暂停该账户写入并完成最终备份，再用候选二进制暂存和运行 `check-data`。升级保留原阶段、owner 和 epoch，普通业务、执行器及迁移 RPC 均不会触发升级。暂存和恢复都需要全新的目标目录，可使用同一代备份在另一个新目录重试。暂存命令只生成单账户文件，替换服务数据目录前须核对完整账户集合及备份时点以后的写入。

演练中的 D1 表仅用于验证诊断读取和回切。生产业务路由、线上 DO 冻结导出、带新增业务写入的回滚，以及真实微信和 Stripe 联调仍待验收。

| 微信接收 → 游标确认 → 账单与回复引用 | 微信的零值消息编号可对应多个不同序号。收件时使用有效序号，确认旧记录属于同一条消息时保留原主键。收件、等待上下文的回复和游标共用事务。 | 在本地 workerd、真实 WebSocket 和 Go SQLite 间重试丢失的 ACK，核对两个相邻的大整数、旧零值回执和过期绑定。公开主分支已独立发布零值修复。上线后的接收巡检验收覆盖 49 个账户、51 个微信链接。 |
| Worker 入口 → 账户路由 → 原生模块 | 部分入口直接取 DO，迁移后会读写旧库。用户 API、支付到账、管理员账户操作、邀请、通知、媒体、接收器和 AGT 回调现在查 D1 路由。每次签名请求携带路由代次。 | 本地原 DO 导出再导入 Go 后，重放原支付两次，余额仍为 42 credits。旧路由版本及冻结账户拒绝业务请求。测试使用隔离的 D1、R2 和真实 SQLite。 |
| 云任务回调 → 回执 → 调度 | 重复回调可能冲掉重试时间或改变结算。Go 校验原始字节签名、任务密钥版本、账户、工作区和上游任务归属，原子保存回执及唤醒时间。 | 接近 1 MiB 的签名请求经公开 Worker 路由抵达 Go。重复获得确认，编号冲突和跨租户请求返回 409。模拟 AGT 服务验证空间用量、重定向、配额格式及请求期间工作区变更。 |
| 个人记录 → 微信链接范围 → 网页展示 | 已删除链接仍可能有历史记录库。Go 根据插件、选中的链接及已保存的范围查询，分页与按币种汇总使用同一组条件。 | 同一套记录在原 DO 和 Go 返回一致的范围、收支、提醒错误、分页、历史空库及非法条件响应。 |

这轮实际演练使用隔离账户和模拟供应商。整账户仍有聊天执行和回复、插件读写、微信绑定管理、个人记录写入与提醒等缺项。后端激活保护继续生效。线上整账户验收需要另行执行。

## 接收器空闲巡检迁移验收

| 链路 | 实现与验证 |
| --- | --- |
| VPS 接收器 → Go 巡检 → Worker | 根因是接收器已经持有健康连接时，账户仍为 60 秒心跳租约反复运行完整闹钟。现在本机 Node 提供有新鲜 pong 的会话，Go 每轮分页比对 D1 登记。在 workerd、D1、真实休眠 WebSocket 及独立 Go 进程的演练中，连续三轮健康扫描产生 0 次账户恢复 RPC，下一次空闲兜底约为 15 分钟。 |
| 消息到达 → 账户处理 | 沿用已持久化的消息确认、去重和账户业务排期。向本地账户投递真实格式的测试消息后，收件箱只有一条，下一次业务闹钟在两秒内。微信上游使用测试数据。 |
| 旧会话、失联 → 回退 → 再接管 | 模拟 pong 中断后只发生一次恢复，账户回到原一分钟巡检。另验证没有健康 Go 心跳时不交接、旧会话回报无法影响新连接、恢复 RPC 失败后 D1 保留重试、Go 恢复后现有连接再次交接，以及移出名单后的回退。 |
| 独立发布 | Linux amd64 包包含 Node 接收器、Go 二进制和两个服务单元。在隔离的 Linux 容器内实际启动并正常停止了巡检命令。它无需账户数据库或加密密钥。后续已在生产 VPS 验证接收器及巡检两个 systemd 单元运行，49 个账户完成交接。线上故障恢复时间及 DO 账单降幅仍待实测。 |
