# 架构与数据流

[返回 README](../README.md)

## 组件

```text
网页 / 微信
    ↓
Hono API（Cloudflare Worker）
    ├── Better Auth → D1：用户、登录、订单、邀请、管理员统计
    ├── PersonalAccount（每个用户一个 Durable Object）
    │     ├── SQLite：渠道、会话、消息、钱包、插件、个人记录
    │     ├── 模型 / 插件网关 → 用户自备的上游 API
    │     ├── R2：图片和受控媒体文件
    │     └── OpenClaw / Hermes ← 用户侧连接器向外连接
    └── 独立提醒 Worker → ReminderScheduler → 账户 RPC → 微信
```

普通网页请求先验证登录，随后只路由到当前用户的账户对象。管理后台使用独立的服务器端角色检查。连接器和消息提醒 Token 仅拥有对应插件的有限权限，不等同网页登录 Cookie。

## 微信消息

每条链接持有独立的凭据、轮询游标、当前模式和会话。消息先经过平台命令解析，再按当前模型或插件派发。

- `/wx ...` 属于微伴，例如 `/wx help`、`/wx status`、`/wx new`。
- `/use 快捷名` 进入或切换插件，`/exit` 返回普通模型。
- `@快捷名 内容` 只调用一次，不修改默认模式。
- 进入远程 Agent 后，其余前导斜杠命令交给 Agent，避免 `/new` 等冲突。

附件先暂存，后续要求与附件合并后派发；暂存有时间、数量和字节限制。语音依赖微信提供的转写文本，当前没有语音合成输出。

## 上下文与计量

渠道保存协议、地址和加密 Key；模型保存模型 ID、提示词和限额。不同模型、插件、会话的上下文不混用。长对话将较早完整轮次整理为摘要，保留最近对话，明确的上下文超限才触发缩减后重试。

平台使用固定版本 tokenizer 计算进入插件的输入和最终返回结果，不信任上游 `usage`。远程 Agent 内部工具和模型消耗由用户自己的运行环境负责。失败且没有可用结果时不扣 credits；钱包以整数单位保存，并对重复结算去重。

## 提醒和异步交付

个人助理的笔记、待办和提醒分别存储；普通提醒不会自动成为待办。独立 `ReminderScheduler` 使用 Durable Object alarm 调度，提醒、每日待办通知、HTTP 消息通知各自维护队列和版本。

记录与待同步版本持久化后登记调度。发布或网络故障后继续重试；旧调度版本不能覆盖用户的修改或取消。外部微信接口发生“已接收但确认丢失”时，最终去重仍依赖上游，不能保证严格的仅一次交付。

网站更新与提醒服务分开发布。原生 Agent 中途退出的任务不会自动重新执行工具，以免重复产生副作用；已完成回复通过持久化发件箱重试。

## 关键位置

| 位置 | 职责 |
| --- | --- |
| `src/server/index.ts` | API 路由、登录和请求边界 |
| `src/server/personal-account.ts` | 账户状态、微信消息、插件与会话协调 |
| `src/server/reminder-scheduler.ts` | 独立提醒调度与恢复 |
| `src/server/llm*.ts`、`context.ts` | 上游协议、工具调用和上下文 |
| `src/server/plugins/` | 内置插件实现 |
| `src/server/wallet.ts`、`billing.ts` | 用量结算、订单、Stripe 校验 |
| `src/server/billing-notifications.ts` | 付款通知持久队列与重试 |
| `src/shared/plugins.ts` | 插件协议与运行时 Schema |

账户协调模块仍较集中。后续可以按会话、微信传输和插件运行分拆，但需保留现有存储兼容和隔离测试。
