# 微伴云端 OpenClaw 方案备忘录

记录日期：2026-10-09。

**状态：方案留存，暂缓开发。** 用户当前仅要求记录讨论结果。本方案不构成实施、部署、采购或修改现有套餐的授权；恢复开发需要用户后续明确提出。

## 产品方向与决策状态

长期目标是提供个人使用的云端 OpenClaw：用户在微伴创建助手，配置自己的模型服务，选择技能，即可通过微信使用，无需在本机安装 OpenClaw 或保持电脑开机。R2 用于长期保存文件、工作区及恢复所需的数据。

用户已提出云端 OpenClaw 与 R2 存储方向，并讨论对 OpenClaw 二次开发的可行性。以下架构、开发顺序和资源套餐均为待验证的建议，尚未确定具体版本、实例规格、费用或上线时间。

建议以 OpenClaw 为基础做云端发行版：保留 Agent 循环、模型适配、工具调用、技能和会话能力，通过云端适配插件、托管服务和少量必要的核心补丁完成集成。优先使用上游公开接口；暂不计划将完整运行时改写为纯 Workers 程序。

## 与现有产品的关系

- 现有微信入口、账号、模型渠道、Plus 权限、credits、消息路由及会话管理可以作为平台基础。
- 现有 OpenClaw 与 Hermes 外部连接方式继续作为用户自托管的选择；云端托管是另一个运行方式。
- 渠道仍只管理模型协议、地址和凭据，功能属于插件或技能，不把二者重新绑定。
- 保留 `@快捷名` 单次调用、`/use` 切换默认插件、`/exit` 退出的交互原则。
- 随手记、记账等可以成为云端助手的技能场景；当前不据此开发独立垂直 Agent。
- 插件市场和用户上传代码仍是后续目标，需要以隔离执行、明确权限和版本管理为基础。
- 当前远端 OpenClaw 连接器主要传输文本及微信转写文字；云端文件输入输出需要单独补充附件引用、授权和交付能力，不能视为已经具备。

## 建议架构

| 层 | 职责 | 初步选择 |
| --- | --- | --- |
| 产品入口 | 微信收发、网页管理、认证、会员及结算 | 复用现有 Workers 服务 |
| 用户运行管理 | 任务队列、实例唤醒、状态、去重和结果投递 | 按用户划分的 Durable Object，具体拆分待评审 |
| Agent 执行 | OpenClaw、工具、技能及子进程 | 每个用户独立的容器或 Sandbox 环境 |
| 文件保存 | 上传资料、生成文件、记忆文档、工作区版本 | 私有 R2 |
| 平台元数据 | 账号、资源配额、实例映射及文件索引 | 现有 D1 / Durable Object，按数据归属划分 |
| 外部能力 | 模型、搜索及第三方服务 | 用户自备 API 和凭据 |
| 唤醒调度 | 消息触发与到期任务触发 | 容器之外的持久化调度 |

平台管理任务和托管资源；OpenClaw 管理其内部会话和执行状态。网页优先通过 Gateway RPC 访问 OpenClaw，不直接读写内部数据库表。上游的[嵌入指南](https://docs.openclaw.ai/gateway/embedding)建议由宿主管理进程，通过公开协议控制运行时，内部文件布局不属于稳定接口。

用户的助手身份和文件长期存在，计算环境可以按需启动。多用户共享平台服务，每个用户的 Agent 执行环境保持隔离；不要求为所有注册用户永久保留运行中的容器。

## 云端适配重点

### 消息与运行生命周期

现有外部连接器由本机主动连接并等待任务。云端版本需要增加平台主动唤醒路径，不能依靠已经休眠的实例继续轮询。

建议流程：平台接收并持久化消息 → 取得该用户的执行租约 → 唤醒实例 → 恢复配置和数据 → 确认可服务 → 派发任务 → 保存结果并投递 → 等待空闲 → 完成必要持久化后休眠。

正在执行任务、运行子进程、保存数据或等待必须保持的交互时，不应直接休眠。实例替换需要排除旧实例继续写入，避免同一工作区出现两个有效写入者。

### R2 与完整恢复

R2 作为对象存储，不直接承担运行中数据库的普通磁盘语义。Agent 执行时使用本地工作目录，文件和数据库分别采用合适的持久化方式。

| 数据 | 建议处理 |
| --- | --- |
| 上传资料、图片和生成产物 | 以账号和任务授权的资产引用保存到 R2 |
| 记忆文档、技能和工作区文件 | 保存文件版本或一致性快照，启动时恢复 |
| OpenClaw SQLite 数据 | 评估 Litestream 复制或一致性备份，验证恢复点和丢失窗口 |
| 运行配置与技能依赖 | 保存可重建配置、固定版本和依赖清单，预装常用依赖 |
| API Key 等凭据 | 平台加密管理，按用户权限注入或代理访问，不混入公开配置和普通文件下载 |
| 平台任务、结算及投递状态 | 保存在平台持久数据库中，不随旧工作区快照回滚 |

OpenClaw 的[实验性 Cloudflare 模板](https://docs.openclaw.ai/install/cloudflare)已经使用 Litestream 向 R2 复制 SQLite，但并不自动恢复全部配置、凭据文件、已安装插件和工作区，不能直接当成完整 SaaS 方案。其 [R2 存储插件](https://docs.openclaw.ai/plugins/cloudflare)提供存储位置，配置该插件不等于启用了自动备份。

文件恢复与任务恢复分别设计。恢复工作区不能自动恢复进程执行现场；已产生外部效果的操作不能无条件重跑。完成任务后应持久保存最终结果，微信发送失败只重发已有结果，不重复调用 Agent 或扣费。

保存记忆文件只是长期记忆的基础，仍需检索和上下文组织，避免每次读取全部资料。

### 定时唤醒与后台任务

OpenClaw 保留任务定义和到期执行判断，平台保存下一次唤醒计划。到点后平台启动实例，由 OpenClaw 处理到期任务，避免两套调度器各自重复执行。

最新上游文档提供 `cron_reconciled`、`cron_changed` 等[外部唤醒同步接口](https://docs.openclaw.ai/plugins/hooks/lifecycle#safe-external-cron-projection)。同步应原子、幂等，并处理旧版本覆盖、删除、禁用和同步失败。实例休眠前需要确认唤醒计划已经持久接受；不能仅依赖进程内回调重试。实施时先确认所选 OpenClaw 版本具备对应接口。

后台结果沿用消息来源语义：当前插件的普通回复不附加来源提示；主动通知和来自当前插件之外的回复附来源、切换或回复说明和分隔符。微信投递窗口过期时需要保存待投递状态，不能承诺云端运行就能绕过微信的投递限制。

### 用户与代码隔离

OpenClaw 的[信任模型](https://docs.openclaw.ai/gateway/security/trust-model)将一个 Gateway 视为一个信任边界。不同账号的 `agentId` 或会话 ID 不能替代执行隔离。

建议每个用户使用独立 Gateway、运行环境、凭据和文件权限。R2 路径前缀只负责组织文件，访问授权必须由平台或受限凭据实施。用户上传的原生插件在该用户的隔离环境运行，不加载到共享的平台进程。

需要定义运行时长、并发、内存、磁盘、网络和文件容量限制。仅使用应用层钩子或提示词，不能限制任意上传代码对宿主的访问。

### 启动优化与上游兼容

先固定上游版本及镜像，预装依赖，关闭无关的渠道发现和后台服务，减少启动扫描及恢复量；确有瓶颈时再做核心补丁。不能通过随意复制部分构建产物来假定获得兼容的轻量运行时。

优先支持文本、网络 API、文件处理及已准备依赖的技能。依赖用户桌面应用、已登录的本地浏览器、摄像头等能力需要额外设备连接；不承诺所有本地技能在云端无修改运行。

维护明确的补丁清单、适配测试、版本升级与数据库迁移策略。回滚程序与回滚数据分别处理，避免旧快照恢复后重复执行任务、恢复过期授权或重复投递。

## 费用与计量边界

现有边界计费规则保持不变：平台独立计数传入插件的文本与最终输出，`credits = (inputTokens + 8 × outputTokens) / 5000 + 已验证输出图片数 × 5`。Agent 内部模型调用、工具日志和推理不重复收取本站对话 credits，上游模型费用仍由用户的 API 承担。

云端托管会新增计算和存储成本。建议另行评估托管套餐或包含运行时长、容量的资源额度；这是待评估选项，不代表调整当前 Plus 或 credits 售价。少量输入也可能触发长时间任务，不能只用边界 token 推算云端成本。

按 2026-10-09 讨论时查询的单价，忽略共享免费额度，R2 标准存储 10 GB 一个月约 $0.15，操作请求另计；分配 4 GiB 内存的容器持续运行 30 天，仅内存约 $25.92，CPU、磁盘、网络及其他服务另计。该示例不代表选定了 4 GiB 规格，也不是实际单用户成本。恢复评估时重新核对 [R2 定价](https://developers.cloudflare.com/r2/pricing/)和 [Containers 定价](https://developers.cloudflare.com/containers/platform/pricing/)。

不将现有 ¥9.9/月、¥88/年的 Plus 直接承诺为无限量全天常驻实例。是否能纳入现有会员，取决于实际活跃时间、实例规格、启动开销和资源限制。

## 恢复开发后的建议顺序

以下是未来的验证顺序，当前均未启动。

1. **版本与扩展点确认**：选择固定版本，确认 Gateway RPC、任务钩子、R2 和数据库布局；验证现有微信连接器的兼容性。
2. **单用户闭环**：以用户自备模型、少量预装技能、独立工作区验证聊天、文件读写、结果交付及休眠唤醒。
3. **恢复与调度验证**：测试正常休眠、强制重启、数据恢复、定时唤醒、任务中断及重复投递；界定可接受的数据恢复点。
4. **多用户托管**：验证身份和存储隔离、实例创建、凭据管理、资源配额及并发情况下的行为。
5. **运行测量与套餐评估**：根据真实数据决定保温时间、实例规格、套餐和是否进一步精简运行时。
6. **插件市场与代码上传**：运行和隔离机制验证后，再逐步开放第三方技能与代码。

关键指标包括首次和再次唤醒时间、空闲内存、完整恢复成功率、未同步数据窗口、定时任务延迟、异常后的重复执行情况，以及每个活跃用户的月度资源成本。指标目标与上线门槛需在恢复开发时确定。
